## 0. Как пользоваться этим ТЗ (для Claude Code)

1. Работать **по этапам** из §15, строго по порядку. Каждый этап начинать в plan mode: прочитать нужные разделы ТЗ и скиллы, составить план, показать его пользователю, затем реализовывать.
2. Каждый этап закрывается только при выполнении его **критериев приёмки** и общего **Definition of Done** (§16).
3. Любое изменение, которое может записать что-то в пульт или вывести звук, проходит ревью агентом `safety-reviewer` до коммита.
4. **Claude Code никогда не обращается к реальному пульту и не воспроизводит звук на реальное железо.** Разработка и тесты идут только на эмуляторе (`127.0.0.1`) и фейковом аудио. Команды на реальном оборудовании запускает только человек (§9.1).
5. Если адрес OSC, формула или поведение пульта не подтверждены скиллом `x32-osc` или фикстурами из реальных дампов, **не угадывать**. Пометить в коде `# UNVERIFIED:` и спросить пользователя, либо добавить пункт в `docs/hardware-checklist.md` для проверки на железе.
6. Документацию библиотек (Textual, Typer, sounddevice, pydantic, numpy/scipy) смотреть через Context7 MCP, а не по памяти.

## 1. Контекст и цель

**Проблема.** В большинстве небольших церквей звуком занимаются волонтёры без подготовки. Система (порталы, саб, иногда фронтфилы и балкон) часто настроена «на слух» или вообще не настроена. Типичные следствия: провал на стыке саба и порталов, «бочка» в голосе, неразборчивая речь, глубокие вырезы на каждом вокальном канале вместо коррекции системы. Профессиональная настройка стоит $1 000–3 000. Готового бесплатного инструмента, который измеряет зал и пишет настройки прямо в X32/M32, нет (см. проектный документ `claude/market-research-autotuning.md`).

**Цель MVP.** Терминальное приложение для macOS, которое за одну репетицию проводит волонтёра через замер и настройку системы на Behringer X32 / Midas M32:

- читает из пульта всё, что можно прочитать, и спрашивает только недостающее;
- пошагово объясняет, куда поставить микрофон(ы) и что нажать;
- измеряет зал одним микрофоном с перестановкой или несколькими сразу (с калибровкой);
- предлагает кроссовер саб/порталы, выравнивание саба (задержка, полярность, уровень) и EQ системы;
- безопасно применяет изменения (diff, подтверждение, undo-файл, чтение записанного обратно);
- перемеряет, проверяет, что стало лучше, иначе предлагает откат;
- сохраняет всё и выдаёт отчёт с рекомендациями, включая то, что EQ не лечит (акустика).

**Основа.** Существующий инструмент `~/sites/my/X32-church` (Python, около 5300 строк): `x32tool/` (osc, writer, dsp, measure, analysis, eqdesign, subtool, x32params, sim, report, cli), `tests/x32_emulator.py`, `tests/test_safety.py`, агенты `acoustics-analyst` и `safety-reviewer`, скиллы `x32-osc` и `room-measurement`. Методика и код проверены на реальном зале 2 октября 2026 года. MVP — новый репозиторий, в который этот код **переносится и обобщается**, а не пишется заново (§15, этап M0).

## 2. Пользователи и сценарий

**Основной пользователь — волонтёр-звукорежиссёр.** Умеет пользоваться пультом на базовом уровне (фейдеры, mute, сцены), не знает, что такое передаточная функция. Терминал открывал редко. Готов потратить 1–2 часа в пустом зале.

**Второй пользователь — опытный звукорежиссёр или инсталлятор.** Хочет быстро, без лишних вопросов, с доступом к цифрам и экспертным командам.

**Главный сценарий (happy path, около 60–90 минут):**

1. Волонтёр подключает Mac к пульту по USB и сети, ставит измерительный микрофон, запускает `ctune`.
2. Программа находит пульт, читает модель, маршрутизацию, выходы, матрицы и EQ. Показывает: «Нашёл X32 Producer, порталы на Matrix 1/2, саб на Matrix 3. Верно?»
3. Спрашивает только то, чего не прочитать: сколько микрофонов, какая модель, есть ли саб физически и где он стоит.
4. Определяет, на каком входе микрофон («постучите по микрофону»), проверяет путь сигнала коротким тихим тоном, подбирает громкость.
5. Даёт план точек замера (ASCII-схема зала), ведёт по раундам «поставьте сюда → Enter → замер → готово».
6. Показывает найденные проблемы простыми словами и предлагает изменения с объяснением «зачем».
7. Применяет выбранное, перемеряет 4+ точки, показывает «до/после» и выносит вердикт.
8. Сохраняет сессию и отчёт, напоминает сохранить сцену на пульте и что проверить на слух.

## 3. Объём MVP

### 3.1 Входит

| Область | Что именно |
|---|---|
| Платформа | macOS 13+ (Apple Silicon и Intel), Terminal.app, iTerm2, встроенные терминалы IDE. Ядро переносимо: тесты ядра идут и на Linux в CI |
| Пульты | Behringer X32 (Full, Compact, Producer, Rack, Core) и Midas M32 (M32, M32R, M32C), прошивка 4.x. Один драйвер `x32` с вариантами моделей |
| Аудио | USB-карта пульта (X-USB, X-LIVE на X32; DN32-USB, DN32-LIVE на M32): воспроизведение и запись в одном дуплексном потоке, 48 кГц |
| Управление | OSC по UDP 10023: чтение всего, запись только в разрешённые области (§9) |
| Режимы замера | 1 микрофон с перестановкой; 2–8 микрофонов одновременно с обязательной взаимной калибровкой |
| Мастер | Пошаговый интерактивный TUI с сохранением прогресса и продолжением после прерывания |
| Анализ | АЧХ по точкам и усреднённая, разброс, RT60/EDT по октавам, качество замера, стык саб/порталы |
| Предложения | Кроссовер саб/порталы; задержка, полярность и уровень саба; EQ системы (Main LR и/или матрицы порталов); аудит EQ каналов (только рекомендации) |
| Применение | Diff, подтверждение, undo-файл, порядок записи «никогда не громче», readback, откат |
| Проверка | Повторный замер, объективный критерий принятия, рекомендация отката |
| Отчёт | HTML (самодостаточный, с графиками) + Markdown + JSON; рекомендации по акустике |
| Языки интерфейса | English, Русский, Українська (инфраструктура для любых языков) |
| Экспертный режим | Неинтерактивные подкоманды — полный список в §12 |

### 3.2 Не входит (non-goals MVP)

- GUI, планшет и мобильные клиенты; Windows и Linux как поддерживаемые платформы (ядро не должно им мешать).
- Другие пульты (X Air, WING, Allen & Heath, Yamaha). Интерфейс драйвера проектируется так, чтобы их можно было добавить (§6.3).
- Запись маршрутизации, phantom, headamp gain, сцен, настроек FX и inserts. Только чтение и инструкции человеку.
- Автоматическая запись EQ на входные каналы. Только аудит и рекомендации.
- Подавление обратной связи (ring-out), STI, мониторы на сцене, фронтфилы/балкон с отдельной задержкой (балкон — только обнаружение и предупреждение).
- Облако, телеметрия, аккаунты, лицензирование и оплата.
- Калибровка SPL по эталону. Допускается необязательная привязка по показанию телефона (§8.5).

Правило зависимостей между слоями (проверяется тестом `tests/unit/test_architecture.py` через разбор импортов):

```

Цикла импортов нет: `safety` не знает о `mixers`.

## 6. Архитектура

### 6.1 Основные потоки

```
          ┌──────────────┐  OSC/UDP 10023 (read + scoped writes)  ┌──────────────┐
          │  X32 / M32   │◄───────────────────────────────────────►│ mixers/x32   │
          │              │  USB audio 32x32 @48k (play + capture)   │ audio/       │
          └──────────────┘◄───────────────────────────────────────►└──────┬───────┘
                                                                          │
   wizard (state machine) ──► measure ──► analysis ──► design ──► safety ──► writer
          │                                                    │
          └──► storage (venue/session) ◄──── report ◄──────────┘
          ▲
        app (Textual)   /   cli (Typer, expert)
```

### 6.2 Мастер: движок отдельно от интерфейса

- `wizard/engine.py` — конечный автомат шагов (§7). Каждый шаг — класс с методами `can_skip(state)`, `run(ctx) -> StepResult`. Взаимодействие с человеком идёт только через абстрактный `Prompter` (вопрос, выбор, подтверждение, «сделайте действие и нажмите Enter», прогресс, живой индикатор).
- `app/` реализует `Prompter` на Textual. Тесты реализуют его скриптом (`ScriptedPrompter`). Так весь мастер проходится в CI без терминала: эмулятор + фейковое аудио + сценарий ответов.
- После каждого шага состояние (`WizardState`, pydantic) сохраняется в `session.json`. `ctune resume` продолжает с последнего завершённого шага. Шаги, изменившие пульт, перед повтором проверяют актуальное состояние пульта.
- Навигация: «Назад» (кроме шагов после записи в пульт — там «Откатить»), «Пропустить» (если шаг необязателен), «Сохранить и выйти». `Ctrl+C` в любой момент — мгновенная тишина (`stream.abort()`), восстановление временных мьютов, сохранение состояния, выход.
- Длительные операции (свипы, чтение сотен узлов) — Textual workers в потоке. UI не блокируется, индикатор показывает прогресс.

### 6.3 Драйвер пульта (расширяемость)

```python
class MixerDriver(Protocol):
    model: ConsoleModel                      # family, model, firmware, capabilities
    def discover(timeout_s: float) -> list[DiscoveredConsole]: ...        # classmethod
    def read_snapshot(self, progress: ProgressCb) -> ConsoleSnapshot: ...   # read-only
    def infer_topology(self, snap: ConsoleSnapshot) -> TopologyGuess: ...
    def usb_audio_map(self, snap: ConsoleSnapshot) -> UsbAudioMap: ...      # USB in N ← source, USB out N → channel
    def meters(self, which: MeterSet) -> Iterator[MeterFrame]: ...
    def writer(self, auth: WriteAuthorization) -> ScopedWriter: ...  # auth issued by safety.authorize()
```

`ConsoleSnapshot` нейтрален к пульту: входы (имя, источник, mute, фейдер, gain, phantom, HPF, EQ), шины, матрицы, main, выходы (источник, задержка), маршрутизация USB, часы/частота, модель. Сырые строки `/node` сохраняются рядом для отладки и отката. Новый пульт = новый пакет в `mixers/` + эмулятор + фикстуры. Скилл `mixer-driver` описывает контракт.

### 6.4 Хранение данных

Корень по умолчанию — `~/ChurchTune/` (переопределяется `CTUNE_HOME`).

```
~/ChurchTune/
├── config.toml                          # язык, последняя площадка, единицы
├── mics/<mic-set-id>/calibration.json   # взаимная калибровка комплекта микрофонов (+ дата)
└── venues/<venue-slug>/
    ├── venue.toml                       # имя, размеры зала, подтверждённая топология, оборудование
    ├── console/<ts>-snapshot.json       # полный снимок пульта (+ raw node lines)
    └── sessions/<ts>-<kind>/            # kind: baseline | sub | verify
        ├── session.json                 # WizardState, версии, решения пользователя
        ├── session.log.jsonl
        ├── points/<point-id>/{meta.json, ir_<mic>.npz, rec_<mic>.flac}
        ├── analysis.json
        ├── proposal.json
        ├── undo/<ts>-<scope>.json
        ├── pending_restore.json         # если есть невосстановленные временные мьюты

```

У всех JSON-файлов есть `schema_version`. Чтение старых версий идёт через миграции в `storage/migrations.py` с тестами.

## 7. Мастер: шаги, автоматизация, вопросы

Главный принцип: **всё, что можно прочитать или измерить, не спрашивать**. Если значение определено автоматически, показать его с пометкой «определено автоматически» и дать подтвердить или исправить одной клавишей. Спрашивать только то, чего нельзя получить.

Над каждым шагом шапка: «Шаг 7 из 13 · Микрофоны». Нумерация с 1 по шагам, применимым к выбранной цели и конфигурации (пропущенные шаги, например S9 при одном микрофоне, не считаются; при изменении состава шагов знаменатель пересчитывается). Дальше — «что сейчас произойдёт» (1–2 предложения) и подсказки клавиш.

### S0. Приветствие и площадка
- Язык (по умолчанию из локали системы), новая или сохранённая площадка.
- Для сохранённой площадки: «В прошлый раз (12.10): X32 Producer, 2 портала + саб, 6 точек. Использовать как основу?»
- Выбор цели: **полная настройка** / **только проверка (verify)** / **только саб** / **только отчёт по прошлой сессии**.

### S1. Проверка Mac (автоматически)
- Разрешение **Local Network** для терминала. Проверка — UDP-пакет на broadcast и наличие ответа или ошибки `EHOSTUNREACH`. Если нет — инструкция с путём в System Settings и названием текущего терминала.
- Разрешение **Microphone** для терминала. Проверка — короткая запись; цифровая тишина (−200 dBFS) на всех входах означает, что разрешения нет.
- Активный VPN (интерфейсы `utun*` с маршрутом по умолчанию) — предупреждение: VPN часто ломает доступ к 192.168.x.x.
- Аудиоустройство пульта найдено, 32 входа/выхода, номинальная частота 48 кГц. Если частота другая — инструкция для Audio MIDI Setup.
- Результат — таблица OK / WARN / FAIL. FAIL блокирует переход дальше, WARN требует подтверждения.

### S2. Подключение к пульту (автоматически)
- Поиск: broadcast `/xinfo` на порт 10023 по всем IPv4-интерфейсам, ожидание ответов 1,5 с; плюс последний известный IP площадки.
- Найден один пульт — подтверждение. Несколько — выбор из списка (IP, имя, модель, прошивка). Ни одного — ручной ввод IP и проверка.
- Проверка задержки OSC и потерь (20 запросов). Прошивка вне 4.x — предупреждение «не проверено».

### S3. Чтение пульта (автоматически)
- Полный снимок (§6.3) с прогресс-баром. Читается всё, что нужно для топологии, маршрутизации, безопасности и аудита: входы 1–32, aux, шины 1–16, матрицы 1–6, main LR/mono, выходы (main 1–16, AES50, aux), маршрутизация USB-карты и user routing, headamps, `-prefs` (часы), EQ, мьюты, фейдеры, имена, задержки, полярность.
- Снимок сохраняется в `console/<ts>-snapshot.json` до любых других действий. Это первая точка отката.
- Пользователю: «Сохраните сцену на пульте: SCENES → свободный слот → SAVE, имя `before-ctune-<дата>`. Это страховка без компьютера». Подтверждение — Enter.

### S4. Топология системы (автоматически + подтверждение)
- Вывод топологии из снимка: какие выходы физически получают сигнал от Main LR, Mono, матриц или шин. Роли определяются по:
  1. источникам выходов и посылам в матрицы;
  2. именам (многоязычный словарь: `sub`, `саб`, `сабвуфер`, `bass`, `main`, `портал`, `front`, `top`, `fill`, `delay`, `балкон`, `balcon`, `monitor`, `мон` …);
  3. фильтрам (LPF около 80–150 Гц — признак саба; HPF — признак топов).
- Показ таблицы «Выход → Путь → Предполагаемая роль → уверенность» и ASCII-схемы. Пользователь подтверждает или меняет роль: `top L`, `top R`, `top mono`, `sub`, `fill`, `delay/balcony`, `monitor`, `not used`.
- Поддерживаемые для настройки в MVP варианты:
  - A. Порталы L/R + саб на отдельной матрице или шине.
  - B. Порталы L/R прямо с Main LR, саб с матрицы или шины. Саб на Main Mono (M/C) — в MVP **только рекомендации** (адреса `/main/m/*` не проверены на железе): программа меряет и показывает, что выставить руками.
  - C. Порталы без саба.
  - Остальное (фронтфилы, балкон, мониторы) — «обнаружено, в MVP не настраивается» и предупреждение, если они включены и звучат во время замера.
- Если саб сидит на Main LR вместе с топами (без отдельного выхода), кроссовер невозможен. Объяснить и предложить вариант для следующего раза (инструкция, как вывести саб на матрицу), продолжить без кроссовера.

### S5. Оборудование: только недостающее
Вопросы задаются только если не выведены из S4 или прошлой сессии:
- Колонки: активные или пассивные с усилителем (влияет на подсказки по уровню); модели (необязательно, свободный текст); количество и расположение саба (под сценой по центру / по краям / подвешен / на полу у стены).
- Размеры зала для плана точек: ширина, длина зоны слушателей, расстояние от сцены до первого ряда. Можно пропустить, тогда используется шаблон «прямоугольный зал».
- Измерительные микрофоны: количество (1–8), модель (ECM8000, dbx RTA-M, Dayton EMM-6, Sonarworks XREF20, другая), файлы калибровки производителя (необязательно, путь к `.txt`/`.cal`).

### S6. Подключение микрофонов и маппинг входов
- Инструкция: подключить микрофоны в стейджбокс или локальные входы, включить +48V на этих входах (с указанием, где на экране пульта). Phantom программа **не включает**, только проверяет.
- **Автоматический маппинг:** «Слегка поскребите по сетке микрофона 1» → программа слушает все 32 USB-входа, находит канал с всплеском, сопоставляет с источником по маршрутизации USB-карты и с headamp. Затем то же для микрофона 2 и т. д. Результат: `Mic 1 → USB in 10 ← AES50-A 10 (headamp 041, +48V ON, gain +50)`.
- Проверки: phantom включён, gain в разумном диапазоне, вход не клиппует.
- **Сигнал измерительного микрофона не должен попадать в колонки никаким путём.** Проверяются все каналы, у которых источник — этот вход (их может быть несколько), их mute, посылы на aux/шины/матрицы, direct out и user routing на физические выходы. Любой открытый путь: предложить временный mute (скоуп `temp_mutes`, §9) или попросить сделать руками; без этого шаг не завершается.
- В конце сессии мьют каналов измерительных микрофонов снимается **только после подтверждения «микрофоны отключены»**. Если пользователь не подтвердил — каналы остаются в mute, в отчёте и на экране — инструкция, что вернуть руками.
- USB-маршрутизация не позволяет снимать микрофон до обработки (не pre-processing) — предупреждение: замер будет включать EQ и динамику канала. Инструкция, как переключить в настройках карты.

### S7. Путь воспроизведения и проверка системы
- Поиск каналов, у которых источник — USB-выходы карты, и их назначения на Main или нужные матрицы. **Посылы этих каналов на aux/мониторные шины** должны быть закрыты (иначе свип уйдёт в мониторы на сцене): предложить `temp_mutes` для мониторных шин или инструкцию. Если есть — подтвердить. Если нет — пошаговая инструкция (какой канал, какой источник, назначить на LR), без записи маршрутизации.
- **Автоматический тест пути:** тихий (−40 dBFS) короткий тон 1 кГц, затем полосовой шум, на USB-выходы → проверка по метрам пульта (канал → main → нужные выходы) и по измерительному микрофону. Определяет задержку системы и что звук действительно идёт из колонок.
- **Проверка колонок по одной** — изоляция только через mute матриц или шин, питающих колонку (у физических выходов X32 mute нет). Если путь колонки не отделим (например, топы прямо с Main LR, а матрица саба тоже питается от Main), этот тест для неё пропускается с объяснением: левый портал, правый портал, саб. Для каждого: слышен ли, в правильной ли стороне (по разнице времени прихода, если ≥ 2 микрофонов), полярность топов L и R одинакова. Найденная перепутка L/R или полярности — отдельная находка в отчёт, а не автоматическое исправление.

### S8. Безопасность и уровень
- Список входных каналов, которые могут дать обратную связь или шум: не замьючены, есть gain, источник — физический вход (не USB и не FX). Варианты: «Замьютить их временно и вернуть в конце» (`temp_mutes`) / «Я замьючу сам» / «Продолжить без этого» (с подтверждением и записью в журнал).
- Подбор уровня: розовый шум, начиная с −50 dBFS, плавный подъём шагами по 2 дБ раз в 0,5 с, пока микрофон в точке 1 не покажет целевой уровень (по умолчанию −20…−12 dBFS RMS). Живой индикатор уровня по каждому микрофону. Подъём останавливается при первом из условий: цель достигнута; выход достиг −6 dBFS (жёсткий предел); микрофон клиппует; уровень на микрофоне превысил цель на 6 дБ (скачок); **уровень выхода поднялся на 12 дБ, а уровень на микрофоне — меньше чем на 6 дБ** (микрофон не тот, отключён или звук не идёт в колонки → стоп и диагностика); пользователь нажал пробел. Важно: −6 dBFS на выходе Mac не ограничивает громкость в зале (дальше gain и фейдеры пульта), поэтому громкость контролируется по микрофону.
- **Уровень свипа** определяется пробными короткими свипами (1 с): старт −30 dBFS, шаг +3 дБ, пока пик записи на микрофоне в точке 1 не окажется в −12…−6 dBFS; ограничения — −6 dBFS на выходе и предел SPL (если есть привязка). Найденный уровень используется для всей сессии; для каждой новой точки проверяется клиппинг.
- Необязательно: «Если у вас есть шумомер или приложение на телефоне, введите показание dB(C) рядом с микрофоном 1». Это даёт привязку dBFS→dB SPL и предел громкости свипа (по умолчанию не больше 90 dB(C) в точке замера).
- Измерение фонового шума по каждому микрофону (3 с тишины) и по октавам. При шуме выше порога — подсказки: вентиляция, диммеры прожекторов (гул 100/120 Гц и гармоники), разговоры.

### S9. Калибровка микрофонов (только если микрофонов больше одного)
- Инструкция с ASCII-рисунком: все микрофоны рядом, капсюли в пределах 10 см, на одной высоте, направлены в одну сторону; в 3–5 м от колонок, вне оси сильных отражений.
- Два свипа → для каждого микрофона относительная АЧХ к медиане комплекта (1/3 октавы), задержка относительно остальных, уровень чувствительности.
- Браковка: отклонение формы > ±3 дБ в 100 Гц–8 кГц после выравнивания уровня, разница задержки > 0,5 мс, высокий шум, инверсия полярности → «Микрофон 3 отличается от остальных: проверьте кабель/микрофон или исключите его».
- Сохранение в `mics/<mic-set-id>/calibration.json` (набор определяется по маппингу и моделям). Повторное использование без переспрашивания до 30 дней, если маппинг совпал. Иначе предложить перекалибровать.
- Если есть файл производителя — сначала применяется он, взаимная калибровка добавляется сверху.

### S10. План точек и замер
- **План:** минимум 8 позиций в зоне слушателей по правилам (§8.3). На ASCII-схеме зала — сцена, колонки (если известны), проходы, точки с номерами. Пользователь может сдвинуть или удалить точку, тогда план перепроверяется.
- **Один микрофон:** последовательность из 8+ позиций, порядок минимизирует ходьбу. Для каждой: «Поставьте микрофон в точку 3 (центральный проход, 6-й ряд), капсюль на высоте 1,2 м, направлен на сцену → Enter. Отойдите от микрофона».
- **Несколько микрофонов:** раунды. В каждом раунде K микрофонов стоят в K точках плана, все пишутся одновременно одним свипом. Число раундов = ceil(N_points / K). Между раундами — «переставьте микрофоны 1–4 в точки 5–8».
- Отсчёт 3 секунды перед свипом (время отойти). Затем свип, по умолчанию 2 усреднения, и проверка качества каждой точки сразу (§8.2). Если качество плохое — причина простыми словами и выбор «повторить / громче / пропустить точку».
- **Саб/топы (если есть саб):** в 4 точках из плана (или во всех, если микрофонов ≥ 4 — тогда один раунд) три стимула в одном потоке: только саб, только топы, вместе. Для этого временно мьютятся соответствующие матрицы/выходы (`temp_mutes`), восстановление сразу после, в `finally` и с `pending_restore.json`.
- Индикатор прогресса: «Точка 5 из 8 · раунд 2 из 2».

### S11. Анализ и предложения
- Анализ (§8.4) и автоматическая сводка простыми словами, по приоритету:
  1. «Саб и порталы гасят друг друга около 100 Гц (−9…−13 дБ во всех точках)» → предложение кроссовера и выравнивания.
  2. «Горб 400–630 Гц +4 дБ — голос звучит "в бочке"» → полоса EQ.
  3. «Зал гулкий: RT60 1,5 с на средних. EQ этого не исправит» → в рекомендации по акустике.
  4. Аудит каналов: «На 9 вокальных каналах вырезы −10…−15 дБ в 200–300 Гц — похоже, так компенсировали зал. После настройки системы их стоит ослабить» → только рекомендация.
- Предложения сгруппированы в **пакеты**: «Кроссовер саб/порталы», «Выравнивание саба», «Уровень саба», «EQ системы». У каждого пакета: что изменится (таблица было → станет), зачем, ожидаемый эффект (прогноз по модели, с оговоркой, что решит проверка), риск. Пользователь отмечает пакеты галочками.
- Порядок применения задан: кроссовер → (перемер саба/топов по требованию) → выравнивание → уровень → EQ системы. Если выбран кроссовер, мастер предлагает после него короткий перемер стыка (S10, только саб/топы) и только потом выравнивание. Так было в реальной сессии.

### S12. Применение
- Перед записью: свежее чтение затрагиваемых параметров; если пульт изменился с момента снимка — показать различия и потребовать решения.
- Diff-таблица «параметр · было · станет · после квантования». Подтверждение — ввод слова `apply` (или локализованного эквивалента), а не одна клавиша.
- Undo-файл сохраняется **до** первой записи. Порядок записи «никогда не громче» (§9.3). Readback каждого параметра. При первом несовпадении — стоп и предложение отката.
- После применения: «Изменения записаны. Сцена на пульте пока **не** сохранена».

### S13. Проверка (verify)
- Перемер: минимум 4 точки, включая худшую точку базового замера и центральную; в мульти-режиме — один раунд со всеми микрофонами.
- Критерии принятия (§8.6) → вердикт: **«Стало лучше»** / **«Без заметной разницы»** / **«Стало хуже — рекомендую откат»** (откат одной клавишей, тоже с diff и подтверждением).
- График «до/после» прямо в терминале (упрощённый, Unicode-блоки) и в отчёте.

### S14. Отчёт и следующие шаги
- Генерация отчёта (§10), путь к файлу, команда `open` для HTML.
- Чек-лист человеку: сохранить сцену на пульте под новым именем; на ближайшем служении проверить на слух список вещей; рекомендации по акустике; что делать с вырезами на каналах (по одному, на слух).
- Восстановление всех временных мьютов с проверкой readback. Пока `pending_restore.json` не пуст, мастер не завершает работу.

## 8. Методика и алгоритмы

Всё ниже — обобщение работающего кода `X32-church` (`dsp.py`, `measure.py`, `analysis.py`, `eqdesign.py`, `subtool.py`). Поведение, проверенное в реальном зале, не менять без причины. Изменения проходят через `dsp-reviewer` и golden-тесты (§14.4).

### 8.1 Стимул и деконволюция
- Экспоненциальный свип (Farina) 20 Гц–20 кГц, 6 с (настраивается 3–12 с), fade-in/out, предзапись 0,5 с, хвост 3,5 с (больше при длинном RT60: хвост ≥ 1,2 × RT60 на 500 Гц из прошлой сессии, максимум 6 с).
- Регуляризованная деконволюция обратным фильтром. Импульсная характеристика (ИХ) на каждый микрофон.
- Воспроизведение и запись — в **одном** дуплексном потоке одного устройства (общий клок, без дрейфа). Задержка определяется по ИХ.
- Усреднение: N свипов (по умолчанию 2) → среднее ИХ после выравнивания по началу записи (без дрейфа сдвиг не нужен; проверка корреляции свипов как метрика стабильности).
- Мульти-микрофон: запись всех нужных USB-входов одним потоком, деконволюция по каждому.

### 8.2 Контроль качества точки (gates)
| Метрика | OK | WARN | BAD |
|---|---|---|---|
| Клиппинг на входе (пик ≥ −0,5 dBFS) | нет | — | есть |
| SNR (уровень свипа к фону в полосе 100 Гц–10 кГц) | ≥ 30 дБ | 20–30 | < 20 |
| PNR ИХ (пик к шуму хвоста; ≥ 45 нужно для T30, ≥ 35 — для T20) | ≥ 45 дБ | 35–45 | < 35 |
| Повторяемость двух свипов (макс. разница АЧХ 1/3 окт, 100 Гц–8 кГц; поэтому минимум 2 свипа на точку) | ≤ 1 дБ | 1–2 | > 2 |
| Xruns/потери в потоке | 0 | — | > 0 |
| Задержка относительно других точек раунда | в пределах геометрии | — | скачок > 2 мс без объяснения |
Пороги — в `config`, с тестами. Каждой проблеме соответствует подсказка человеку (не цифры, а действие).

### 8.3 План точек
- Не меньше 8 позиций в зоне слушателей. Исключить передние и задние 15–25 % глубины (они идут как контрольные, не в среднее). Не ближе 1 м к стенам (лучше 2–3 м, если зал позволяет). Высота капсюля 1,2 м (уши сидящего). Не ставить основную точку на оси симметрии точно по центру и не в точке схождения осей порталов. Расстояния между соседними точками разные (избегать регулярной сетки).
- Генерация плана: по размерам зала (или шаблону) — квази-случайная выборка (Halton) в разрешённой области с ограничениями, затем ручная правка. Точки для саба/топов — 4 из плана, разнесённые по ширине и глубине.
- Сохранение плана в `venue.toml`, чтобы verify в следующий раз шёл по тем же точкам (с подписями «у 6-го ряда, центральный проход»).

### 8.4 Анализ
- АЧХ: окно ИХ (частотно-зависимое или фиксированное, как сейчас), сглаживание 1/6 октавы, сетка 1/24 октавы для расчётов. Нормировка каждой точки к 0 дБ в 500–2000 Гц.
- Коррекции микрофонов: файл производителя + взаимная калибровка (§S9). Выше 10 кГц без калибровочного файла — пометка «ориентировочно» во всех выводах.
- Среднее: энергетическое по точкам; разброс σ по частоте; классификация особенностей: **общие** (в ≥ 75 % точек, малый σ) — кандидаты для EQ; **позиционные** (большой σ, узкие провалы) — не трогать.
- RT60 (T20/T30), EDT по октавам 63 Гц–8 кГц (Шрёдер), BR (bass ratio). Пометка, если T20/T30 расходятся > 10 %.
- Стык саб/топы: отдельные и суммарные отклики в fc/2…2fc, прямой звук (окно 60 мс), уровни на частоте раздела.
- Опция «зал будет заполнен людьми»: поправка целевой кривой на средних/высоких (по умолчанию выключена, с пояснением).

### 8.5 Проектирование изменений (design)
- **Кроссовер.** Если у пути саба нет ФНЧ или у топов нет ФВЧ, либо найдены «костыли» (полки, вырезы на матрице саба, VEQ на топах на стыке) → LR24 на частоте fc. fc выбирается из диапазона 80–120 Гц по измеренным откликам (где топы ещё в пределах −6 дБ от своего уровня 200–1000 Гц и саб в рабочей зоне). По умолчанию 100 Гц. Костыли удаляются в том же пакете, с объяснением.
- **Выравнивание.** Поиск задержки ±15 мс (шаг 0,1 мс) и полярности, максимизирующих сумму и ровность в fc/2…2fc по всем точкам стыка (взвешенно). Изменение < 1 дБ выигрыша → «менять не нужно». Задержка добавляется тому пути, который приходит раньше. Если задерживаются топы, задержка добавляется и на остальные выходы с той же программой (fill/балкон), чтобы не нарушить их выравнивание.
- **Уровень саба.** Разница уровней саба и топов на fc → коррекция фейдером матрицы/шины саба: не больше ±10 дБ за пакет, итог не выше 0 дБ (в реальном зале понадобилось +8,2 дБ). Если нужно больше — режим подсказки: программа показывает значение, пользователь выставляет руками.
- **EQ системы — куда ставить** определяется топологией: проблема, общая для всей системы (и топов, и саба), — в EQ общего пути (Main LR, если от него питаются и топы, и матрица саба — так было в реальном зале: 480 Гц и мода 50 Гц на Main LR); проблема только топов — в EQ матриц топов (одинаково на L и R); проблема только саба — в EQ пути саба. **Фильтры кроссовера никогда не ставятся на общий путь** — только на отдельные пути саба и топов. Если топы идут прямо с Main LR без матриц, ФВЧ кроссовера поставить некуда → кроссовер в режиме подсказки с инструкцией. Правила из `eqdesign.py`: ≤ 6 полос с учётом занятых; полосы с фильтрами-срезами не трогать; сначала вырезы; подъёмы только широкие (Q ≤ 1,4) и ≤ +3 дБ; не поднимать узкие провалы и нули; отдельные вырезы глубже −9 дБ или с Q > 6 — только с обоснованием; учитывать EQ, который стоял во время замера; существующие узкие вырезы (возможно, от обратной связи) не удалять, а максимум ослаблять наполовину, с предупреждением. Цель: ровно до 1 кГц (опция +3 дБ ниже 100 Гц), выше −1 дБ/окт; `--tilt` настраивается. Оптимизация (least squares) по средней с весом по уверенности.
- **Аудит каналов.** Линтер по входным каналам: отсутствие HPF на вокале и речи; HPF выше 150 Гц на вокале; вырезы глубже −9 дБ; одинаковые вырезы на многих каналах (признак компенсации зала); экстремальные подъёмы > +6 дБ; фантом на динамических микрофонах (по имени — только подсказка). Только рекомендации.

### 8.6 Критерии принятия verify
Обозначения: `D(p, f)` — отклонение АЧХ точки p от цели (дБ) на третьоктавной сетке; сравниваются **одни и те же точки** базового замера и verify (только те, что есть в обоих).
- `M` = RMS по частотам 60 Гц–10 кГц отклонения **энергетически усреднённой** АЧХ от цели.
- `W` = для каждой точки RMS её `D(p, f)` в 80 Гц–8 кГц; «худшая точка» — точка с максимальным `W` в **базовом** замере; `ΔW_worst` = её `W` после − до.
- `ΔB` = максимум по точкам и по полосам 80 Гц–8 кГц ухудшения `|D|` (после − до) — ловит локальные ухудшения.
- `Δσ` = изменение среднего по частотам 100 Гц–4 кГц разброса между точками.
- Для пакета выравнивания: `J` = уровень суммы саб+топы на fc и глубина провала в fc/2…2fc.

| Вердикт | Условие |
|---|---|
| **Стало лучше** | `M` уменьшилось ≥ 0,5 дБ (для чистого выравнивания — `J` улучшилось ≥ 1 дБ) **и** `ΔW_worst ≤ +0,5` **и** `ΔB ≤ 1,5 дБ` **и** `Δσ ≤ +0,5` |
| **Стало хуже** (предложить откат) | `M` выросло ≥ 0,5 дБ **или** `ΔW_worst > +1` **или** `ΔB > 3 дБ` **или** `Δσ > +1` |
| **Без заметной разницы** | всё остальное |

Пороги — в `config`, у каждого тест на синтетических данных.

## 9. Безопасность (главный нефункциональный приоритет)

Цена ошибки — воскресное служение: обратная связь через открытый измерительный микрофон, погасшие порталы, сломанная маршрутизация, громкий свип по людям. Вся модель безопасности переносится из `X32-church` и расширяется. Тесты безопасности не ослабляются никогда.

### 9.1 Правила для разработки
- Claude Code и тесты работают **только** с эмулятором на `127.0.0.1` и фейковым аудио. В коде есть guard (`platform/devsafe.py`, одна функция, тесты в обе стороны): режим dev-safe включён, если `CTUNE_DEV_SAFE=1` **или** задана переменная `CLAUDECODE` (Claude Code выставляет её в своих командах — проверить на текущей версии; если нет — оставить только `CTUNE_DEV_SAFE`, которую задаёт `.claude/settings.json`). В dev-safe драйвер отказывается подключаться к не-loopback адресу, **discovery шлёт только на 127.0.0.1 (никакого broadcast)**, проверка Local Network в S1 не шлёт пакетов, аудиобэкенд отказывается открывать реальное устройство. `CTUNE_DEV_SAFE=0` не отключает режим, если есть `CLAUDECODE`.
- Хук `.claude/hooks/guard_console.py` блокирует команды Bash с приватными IPv4 и `.local`-именами, с `ctune` без `CTUNE_DEV_SAFE=1`, с попытками снять guard (`CTUNE_DEV_SAFE=0`, `unset`, `env -u`), с прямой отправкой UDP на 10023/10024. Хук — вторая линия защиты; первая — guard в коде.

### 9.2 Скоупы записи (allowlist)
Писать в пульт может только `mixers/x32/writer.py`, и только через объект `ScopedWriter`, выданный модулем `safety` для конкретного скоупа. В каждом скоупе явный список регулярных выражений путей и лимиты значений.

| Скоуп | Пути (X32/M32) | Лимиты |
|---|---|---|
| `temp_mutes` | `/ch/NN/mix/on` (каналы измерительных микрофонов и открытые входы — S6, S8), `/bus/NN/mix/on` (мониторные шины — S7), `/mtx/0N/mix/on` (изоляция колонок и замер саб/топов — S7, S10), `/main/st/mix/on` (только замер саб/топов, если иначе путь не отделить) | Только значение 0 (mute) и восстановление исходного значения из снимка. `pending_restore.json` — до первой записи. Восстановление: в `finally` и при `Ctrl+C` — сразу (кроме каналов микрофонов, см. S6); при следующем запуске — **только после свежего чтения пульта, показа diff и подтверждения** (ручные изменения за это время не перетираются) |
| `system_eq` | `/main/st/eq/[1-6]/(type\|f\|g\|q)`, `/main/st/eq/on`; `/mtx/0[1-6]/eq/[1-6]/(type\|f\|g\|q)`, `/mtx/0[1-6]/eq/on`; `/bus/NN/eq/…` (только если саб на шине; UNVERIFIED → режим подсказки до проверки) | Подъём ≤ +3 дБ (Main/топы), ≤ +6 дБ (саб); полосы с фильтром-срезом менять только в пакете «кроссовер» и только на band 1 (HPF) / band 6 (LPF) отдельных путей; выключать EQ, где есть срез, запрещено; **включать EQ можно только если все его полосы проходят те же лимиты**; значения предварительно квантуются |
| `levels` | `/mtx/0N/mix/fader`, `/bus/NN/mix/fader` — только для пути саба | Изменение ≤ ±10 дБ за пакет относительно свежего чтения; итог ≤ 0 дБ; если суммарно относительно **первого снимка площадки** (`venue`) больше ±12 дБ — только с отдельным предупреждением и подтверждением; Main fader **никогда** |
| `delay` | `/outputs/main/NN/delay/(on\|time)` | ≤ 50 мс; при включении — сначала `time`, затем `on` (иначе на мгновение включится старое значение); write UNVERIFIED → режим подсказки до проверки на железе |
| `polarity` | `/mtx/0N/preamp/invert` для пути саба (матрица) | Только переключение, только в пакете «выравнивание»; write UNVERIFIED → режим подсказки до проверки. Саб на шине — полярность только подсказкой |

Никогда: маршрутизация (`/config/*`), headamp и phantom, сцены и снапшоты (`/-action`, `/save`, `/load`, `/-snap`), FX и inserts, EQ, динамика и фейдеры входных каналов, Main fader, настройки карты, `-prefs`, любые «действия» без аргументов вне allowlist чтения.

### 9.3 Порядок записи и транзакционность
- Undo-файл (все затрагиваемые параметры, исходные значения и строки `/node`) — до первой записи.
- **Порядок записи — одно правило:** ни в одном промежуточном состоянии модельная АЧХ любого пути не превышает `max(до, после) + 0,5 дБ` на любой частоте 20 Гц–20 кГц. Порядок строит `safety.order_plan()`, а property-тест проверяет правило симуляцией всех промежуточных состояний (модели полос EQ X32 — из `design`). Базовый алгоритм: (1) фейдеры вниз и мьюты; (2) для каждой полосы EQ, где меняется type, f или q: сначала нейтрализовать полосу (`g → 0 дБ`, для срезов — смена только в пакете кроссовера, с отдельной проверкой), затем type, f, q, затем целевой g; полосы, где меняется только g вниз, — сразу; (3) подъёмы g и фейдеры вверх — в конце; (4) задержка — `time`, затем `on`.
- Readback каждого параметра (запрос значения + `/node`), сравнение по индексу шага квантования. Несовпадение → стоп, сообщение и предложение отката уже записанного.
- Повторная запись того же значения пропускается (идемпотентность).
- `safety.authorize(plan, undo_path, confirmation)` выдаёт `WriteAuthorization` (скоуп, упорядоченный план, путь undo-файла, токен подтверждения); `writer` без неё не работает.
- **Откат (undo) и restore** тоже начинаются со свежего чтения: если текущее значение отличается от ожидаемого «после», показать diff и спросить, что делать (не перетирать ручные изменения молча).
- Подтверждение человеком — ввод слова, а не Enter. В неинтерактивном режиме — флаг `--yes-i-am-at-the-console` и обязательный путь к proposal-файлу.

### 9.4 Звук
- Ничего громче −6 dBFS пик не уходит с компьютера (жёсткий лимитер в бэкенде; тест).
- Свип по умолчанию −24 dBFS; подъём только через шаг уровня S8; если есть привязка SPL — не выше 90 dB(C) в точке (настраивается, максимум 95).
- Fade-in/out на всём. `Ctrl+C` → `stream.abort()` (мгновенная тишина), восстановление мьютов, сохранение. В Textual `Ctrl+C` — это клавиша, а не SIGINT: приложение явно привязывает `ctrl+c` и пробел к действию «тишина» на всех экранах (с тестом через `Pilot`), а вне TUI ставится обработчик SIGINT.
- Перед первым звуком в сессии — экран-предупреждение: «Сейчас прозвучит тестовый сигнал. В зале не должно быть людей с чувствительным слухом рядом с колонками. Наушники снимите».
- Watchdog: если OSC-связь потеряна во время шага с временными мьютами — немедленная остановка звука и попытки восстановления каждые 2 с; на экране — инструкция, что вернуть руками.

### 9.5 Ревью
Любое изменение в `mixers/*/writer.py`, `mixers/*/client.py`, `safety/`, `audio/` (уровни, лимитер), шагах S6–S13 или в формате undo проходит агент `safety-reviewer`. Тесты `tests/unit/safety/*` и `tests/integration/test_safety_e2e.py` должны покрывать все пункты §9.2–9.4 (покрытие строк `safety/` и writer — 100 %).

## 11. Интерфейс и тексты

- Скилл `wizard-ux` — обязательные правила: один вопрос на экран; сначала «что произойдёт», потом действие; обнаруженное показывается как подтверждение, а не вопрос; простые слова, термин — с пояснением при первом появлении (глоссарий в каталоге); каждая ошибка — что случилось и что сделать; цвет никогда не единственный носитель смысла (символы ✓ ! ✗ + текст); работает в 80×24; горячие клавиши видны внизу; не больше 3 действий на экране.
- Все строки — в `i18n/locales/<lang>/*.ftl`. В коде только ключи. Тест: все ключи есть во всех языках, нет неиспользуемых, плейсхолдеры совпадают.
- Числа и единицы форматируются по локали (запятая в ru/uk). Единицы — Гц, кГц, дБ, мс, м.
- Агент `wizard-ux-reviewer` проверяет новые экраны и тексты (прогоняет мастер на эмуляторе, смотрит snapshot-тесты).

## 12. Команды CLI

```
ctune                       # = ctune wizard
ctune wizard [--venue NAME] [--lang ru] [--goal full|verify|sub|report]
ctune resume [SESSION]

ctune measure --plan venue  # экспертный замер по плану, без мастера
ctune analyze [SESSION]
ctune propose [SESSION] [--tilt -1] [--packages crossover,align,level,eq]
ctune apply PROPOSAL [--dry-run]
ctune undo UNDOFILE [--dry-run]
ctune restore               # восстановить pending_restore.json
ctune verify [--points p1,p4,...]
ctune report [SESSION] [--for-chat] [--open]
ctune emulator [--model X32P|M32|...] [--fixture PATH]   # dev: эмулятор на 127.0.0.1, печатает порт
ctune selftest              # встроенная самопроверка установленного пакета: эмулятор в процессе + фейковое аудио,
                            # короткий сценарий мастера (чтение → замер 2 точек → анализ → предложение → dry-run apply)
```
`ctune measure --plan venue` — замер по точкам плана, сохранённого в `venue.toml` (без вопросов мастера).

Глобальные опции и переменные окружения:

| Опция | Переменная | Значение |
|---|---|---|
| `--console HOST[:PORT]` | `CTUNE_CONSOLE` | адрес пульта (по умолчанию — discovery / последний известный площадки) |
| `--audio NAME\|fake` | `CTUNE_AUDIO` | аудиоустройство или `fake` (симулятор зала) |

Коды выхода: 0 — успех; 1 — ошибка пользователя или ввода; 2 — нет связи или устройства; 3 — отказ безопасности; 4 — readback не совпал; 130 — прерывание. Неинтерактивные команды печатают Rich-таблицы, флаг `--json` даёт машиночитаемый вывод.

## 14. Тестирование

### 14.1 Уровни
- **Unit** (быстро, без IO): кодек OSC, параметры и квантование, парсинг `/node`, вывод топологии, DSP (синтетические ИХ с известным ответом), анализ, design, safety-лимиты, i18n.
- **Property-based** (hypothesis): квантование ↔ обратное; писатель никогда не пропускает путь вне скоупа; порядок записи не повышает уровень ни в один момент; undo(apply(x)) == x на эмуляторе.
- **Integration**: драйвер ↔ эмулятор (UDP на loopback); аудио — фейковый бэкенд с симулятором зала (`sim.py`: моды, RT60, нули, задержки, несколько микрофонов с разной чувствительностью, проблемный стык саб/топы).
- **E2E мастера** (`tests/e2e/`): `ScriptedPrompter` + эмулятор + фейковое аудио проходят весь мастер для сценариев A/B/C, 1 и 4 микрофона, прерывания и resume, отказа readback, потери связи во время temp_mutes.
- **TUI**: Textual `Pilot` + snapshot-тесты ключевых экранов в 80×24 и 120×40, ru и en.
- **Golden**: реальные данные зала 2026-10-02 (ИХ 6 точек до и после, дампы) → анализ и предложения в допуске от того, что было реально применено и проверено (кроссовер ~100 Гц LR24; горб ~480 Гц; мода ~50 Гц; решение «задержку не ставить»).

### 14.2 Эмулятор
Перенести `tests/x32_emulator.py` и расширить: модели X32/M32 (строки `/xinfo`), разные варианты маршрутизации и топологии (фикстуры из реальных дампов + синтетические), запись в разрешённые пути матриц/шин/выходов с квантованием и readback, мьюты и фейдеры, метры с реальной структурой блоба, инъекция сбоев (потеря пакетов, задержки, «сдвинутое» значение при readback, обрыв связи).

### 14.3 Покрытие

## 17. Риски и открытые вопросы

| Риск / вопрос | Как обращаемся |
|---|---|
| Адреса OSC для шин, мьютов, полярности, выходов на M32 и других моделях не проверены на железе | Только то, что подтверждено скиллом и фикстурами; остальное `# UNVERIFIED` + чек-лист; на M32 до проверки — режим «только предложения» |
| Имена CoreAudio-устройств карт (X-USB, X-LIVE, DN32-USB, DN32-LIVE) | Список кандидатов + выбор пользователя + запись фактического имени в venue |
| Маршрутизация USB не pre-processing на чужих пультах | Обнаружение и инструкция (S6) |
| Саб не на отдельном выходе | Объяснить и пропустить кроссовер (S4) |
| Волонтёр не понимает, что произошло | Скилл `wizard-ux`, простые тексты, отчёт с чек-листом |
| Автоматика сделала хуже | Критерии §8.6, откат одной клавишей, консервативные правила EQ |
| Лицензия (GPL vs двойная) | Решение владельца до публичного релиза |
| Название проекта | Проверить занятость до публикации |
| Реальные ИХ зала в репозитории (размер, приватность) | Сжать (FLAC/npz), согласовать с владельцем, можно держать в отдельном release-артефакте |

## 18. Глоссарий (для текстов интерфейса и документации)

- **Портал / топы** — основные колонки по сторонам сцены.
- **Саб** — сабвуфер, колонка для низких частот.
- **Кроссовер** — разделение частот: низы идут в саб, остальное — в порталы.
- **Свип** — тестовый сигнал, плавно идущий от низких частот к высоким.
- **АЧХ** — насколько громко система воспроизводит разные частоты.
- **RT60** — время, за которое звук в зале затихает на 60 дБ; показывает, насколько зал «гулкий».
- **Readback** — проверка, что пульт действительно принял записанное значение.
- **Undo-файл** — сохранённые прежние значения для отката.
