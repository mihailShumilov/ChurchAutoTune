Roadmap

Where ChurchTune is today

ChurchTune is built in eight milestones, one after another. Each one ends only when its tests pass. This page is updated whenever a milestone moves.

Last updated: 14 October 2026

Pre-alpha. Not ready for use on a live system. It runs only from the source code. The guided wizard reads the console, measures, proposes changes and can now write them, but this has been tested only against the console emulator and a simulated hall, never on a real console.

In short

  • Done: M0, the foundation. The working tool from the real hall session is now a clean, tested app core.
  • Done, in review: M1 (console driver), M2 (measurement engine), M3 (guided wizard) and M4 (analysis and proposals). Each one waits for review in its own pull request.
  • In progress: M5. Done so far: applying the chosen changes within safety limits, undo, and the check measurement. Still to come: temporary mutes and the separate subwoofer and main-speaker measurement in the wizard, a warning for big subwoofer level changes, and a mode that runs without questions. None of it has been tried on a real console yet.
  • After that: M6 (report) and M7 (pilot in real churches and release 0.1.0). Nothing is released yet.

Want to try what exists? See the guide.

Milestones

The milestones come from the project specification (in Russian). Details may change as the work goes on.

  1. M0. Foundation

    Done

    Move the proven hall tool into a new, layered, tested app without changing what it does.

    Delivered

    • The working tool ported into clean layers: console protocol, safety policy, measurement, analysis, design and reports.
    • Read-only console client and a single, separate writer that needs a scoped permission from the safety policy, with readback of every value.
    • Golden tests on the real hall session of 2 October 2026: the new code must give the same proposals.
    • A dev-safe mode: with CTUNE_DEV_SAFE=1 only the emulator on 127.0.0.1 and simulated audio are accepted.
    • A transitional expert command line (ctune, Russian texts for now) and ctune hwcheck for the two writes never checked on a console.
    • Open-source project files: contributing guide, code of conduct, security policy, issue forms, CI.

  2. M1. Console driver

    Done, in review

    Find the console on the network and understand how the church's system is wired, by reading only.

    Delivered

    • Discovery: finds the X32 or M32 on the network without typing its address.
    • Model and firmware detection; full features only for a checked model and firmware pair (today the X32 Producer with firmware 4.09).
    • A full read-only snapshot of the console settings: inputs, buses, matrices, mains, outputs, preamps, USB routing.
    • Mapping of the USB audio channels.
    • Topology inference: which matrix, bus or output feeds the main speakers and the subwoofer, with a confidence level and reasons, also from speaker names in several languages.
    • An emulator with several console variants, reply delay and packet loss; fourteen test layouts.
    • ctune doctor, ctune snapshot, ctune emulator and the --emulator option.

    Review

    • Pull request #8 (not merged into the main branch yet).

    How you can help

    • Read-only console dumps of other models, firmware versions and routings. See the contributing guide.

  3. M2. Audio and measurement engine

    Done, in review

    Measure reliably with one or several microphones, at safe levels.

    Delivered

    • Several microphones in one audio stream, real or simulated, and a stop that silences the sound within 50 ms.
    • Finding which input each microphone is on (“scratch the microphone”).
    • Calibration of a set of microphones against each other, with rules that reject a faulty microphone.
    • Level ramp with pink noise, background noise per octave, a signal path check, a speaker-by-speaker check, multi-microphone rounds, and a separate subwoofer and main-speaker measurement with temporary mutes that are always restored.
    • ctune devices, ctune mics map, ctune mics calibrate, ctune noise, ctune pathcheck, and a simulated four-microphone hall behind --audio fake.

    Review

    • Pull request #9 (not merged into the main branch yet).

  4. M3. Guided wizard

    Done, in review

    The step-by-step screen app for volunteers.

    Delivered

    • Plain ctune starts a guided wizard of 13 steps (12 with one microphone). Progress is saved after every step; ctune resume continues.
    • A full-screen terminal interface with tables and live level meters. Ctrl+C or Space stops the sound on every screen, Esc goes back, Ctrl+Q saves and quits.
    • A line interface for screen readers and scripts: ctune wizard --plain.
    • Interface in English, Russian and Ukrainian.
    • Before any sound the wizard reads the console again and refuses to play while a measurement microphone channel could feed back. Every sound has a warning screen, and measurement rounds count down 3 seconds.

    Not yet

    • The wizard reads the console and measures. Proposals came with M4; applying them comes with M5.

    Review

    • Pull request #10 (not merged into the main branch yet).

  5. M4. Analysis and proposals

    Done, in review

    Turn measurements into a short list of safe, explained changes.

    Delivered

    • After the measurement the wizard proposes changes in packages, one screen each: a before → after table, why, the expected effect and the risk, then the question “Add … to the change plan?”. When you leave a package out, the later ones are designed again without it. Your choices are saved in proposal.json.
    • In the wizard this is the system EQ for now. The crossover, the subwoofer alignment and the subwoofer level need the subwoofer and the main speakers measured separately, which comes with M5: set blind, a crossover can leave a gap in the bass.
    • A measurement point plan: at least 8 seats in the middle of the hall, off the centre aisle, each described in words with distances (“front rows, left, about 6 m from the stage, 3.5 m left of the centre aisle”). A simple map highlights the seats of the current round. The plan is kept for the venue.
    • Advice on the input channels, which the program never changes itself: voices without a low cut or with a very high one, narrow cuts that probably protect against feedback (make them at most half as deep, at a rehearsal, with the monitors on), cuts shared by many channels, deep cuts (check them 3 dB at a time), big boosts, and phantom power on dynamic microphones.
    • Tested on a simulated hall with known defects: a late, inverted and too loud subwoofer, a 500 Hz bump, a 50 Hz room mode and a narrow 800 Hz dip in two seats. The proposals fix the first ones and leave the narrow dip alone.

    Not yet

    • M4 itself writes nothing to the console. Applying, undo and the check measurement are part of M5.
    • It has been tested only on simulated halls, not at a real console.

    Review

    • Pull request #11, which builds on #10 (not merged into the main branch yet).

  6. M5. Apply, undo, verify

    In progress

    Write the chosen changes safely, check them, and undo if the result is not better.

    Done so far

    • The wizard step “Apply the changes”: it reads the console again, shows every setting with its present and new value, and writes only after you type a word (apply, применить or застосувати).
    • The old values are saved before the first write. The writes come in an order that never makes the sound louder in between, and every value is read back. If a value does not read back, the wizard stops and offers to put back what was written.
    • If the console changed since the measurement, the plan is refused: measure again.
    • Output delay and polarity are shown as values to set by hand.
    • ctune apply-packages proposal.json does the same from the terminal. ctune undo puts the old values back where they were not changed by hand since.
    • The wizard step “Check measurement”: at least four seats are measured again, and by fixed rules it says “better”, “no noticeable difference” or “worse”. When it got worse, it offers the undo right away. The last screen reminds you to save the scene under a new name.

    Still to come

    • Temporary mutes and the separate subwoofer and main-speaker measurement in the wizard. Until then the wizard never proposes a crossover.
    • A warning for big changes of the subwoofer level.
    • A mode that runs without questions.

    Not tried on hardware

    • All of this is tested only against the console emulator and the simulated hall. Rows 22–25 of the hardware checklist must be run by a person in a real hall before anyone relies on it.

    Done when

    • All safety tests pass, including injected faults such as a readback mismatch or a lost connection.

  7. M6. Report

    Planned

    A report you can keep, print or share.

    What it delivers

    • HTML, Markdown and JSON reports with plots, readable offline, plus a short summary for a forum or chat.

  8. M7. Pilot and release 0.1.0

    Planned

    Prove it in real churches and make the first release.

    What it delivers

    • The hardware checklist run by people at real consoles, and fixes.
    • README in three languages, installation with one command, version 0.1.0.

    Done when

    • The full wizard runs on a real X32 Producer without touching the code, and the results are no worse than the manual session of 2026-10-02.

Not in the first version

To keep the first version small and safe, these are left out on purpose:

  • Other consoles (X Air, WING, Allen & Heath, Yamaha). The driver is designed so they can be added later.
  • A graphical app, tablet or phone apps. Windows and Linux as supported platforms.
  • Changing routing, phantom power, preamp gain, scenes, effects or inserts. ChurchTune only reads them and tells you what to do.
  • Writing EQ to input channels. It only reviews them and gives advice.
  • Feedback suppression (ring-out), speech intelligibility (STI), stage monitors, and separately delayed front-fill or balcony speakers (a balcony is only detected, with a warning).
  • Cloud, telemetry, accounts, licences or payments.

To follow progress, watch releases on GitHub or read the changelog.
