Guide

Using ChurchTune today

An honest guide to what you can do now, and what is coming. It grows with every milestone.

Last updated: 14 October 2026

Pre-alpha. The guided wizard exists, but so far it only reads the console and measures: it does not propose or apply any changes yet. It runs from the source code only. Do not use it on your church's live system yet. See the roadmap.

What you can do today Now

  • Anyone comfortable with a terminal can try the guided wizard on the built-in console emulator with a simulated hall: no console, no speakers, no sound. See Try the wizard without hardware.
  • Developers and testers can install the project, run the tests and try the expert command line against the emulator.
  • Console owners can run a hardware check at a real X32 or M32 and report the result. This is the most valuable help right now.
  • Volunteers who want to tune their church system: please wait. The wizard does not propose or apply changes yet (milestones M4 and M5). Watch releases on GitHub to hear when it is ready.

Equipment you will need

For the real tuning, later. Nothing here is needed to try the developer version.

  • A Mac (the app is made for macOS).
  • A Behringer X32 or Midas M32 with firmware 4.x and a USB audio card: X-USB or X-LIVE in an X32, DN32-USB or DN32-LIVE in an M32. The test sounds are played and recorded through this card.
  • A USB cable from the Mac to the console, and a network connection (cable or Wi-Fi) to the console, which ChurchTune uses to read its settings.
  • A measurement microphone, for example a Behringer ECM8000, with a stand and an XLR cable to a console input. ChurchTune can also use several microphones at once and calibrate them against each other; this has been tested only with simulated microphones so far.
  • An empty, quiet hall and about 1–2 hours.

For developers and testers

Everything below runs only against an emulator on your own computer and simulated audio. Always put CTUNE_DEV_SAFE=1 in front of commands that run the app or the tests: the code then refuses any real console and any real audio device.

1. Install

You need macOS or Linux, Python 3.12 and uv (uv can install Python for you). On Debian or Ubuntu also install libportaudio2 libsndfile1.

git clone https://github.com/mihailShumilov/ChurchAutoTune.git
cd ChurchAutoTune
uv sync

2. Run the tests

CTUNE_DEV_SAFE=1 uv run pytest -q                # all tests: console emulator + simulated audio
CTUNE_DEV_SAFE=1 uv run pytest tests/golden -q   # the real hall session of 2026-10-02

3. Try the expert command line on the emulator

Until pull requests #8–#10 are merged, the commands below live on the m3-wizard branch. In your clone:

git checkout m3-wizard
uv sync

The quickest way is the global --emulator option: it starts a console emulator inside the program for that one command.

CTUNE_DEV_SAFE=1 uv run ctune --emulator doctor     # check the computer and the console, explain the speaker layout
CTUNE_DEV_SAFE=1 uv run ctune --help                # all commands

You can also run the emulator on its own in one terminal (it prints its port and runs until Ctrl+C) and point commands at it from a second terminal, replacing PORT:

CTUNE_DEV_SAFE=1 uv run ctune emulator --model X32P
CTUNE_DEV_SAFE=1 uv run ctune --console 127.0.0.1:PORT --audio fake --home /tmp/ctune-demo doctor

The output of most expert commands is still in Russian; the wizard below is translated. The expert command line stays as a tool for developers next to the wizard.

4. Before a pull request

CTUNE_DEV_SAFE=1 uv run ruff format --check . && uv run ruff check . && uv run mypy \
  && CTUNE_DEV_SAFE=1 uv run pytest --cov --cov-report=json && uv run python scripts/check_coverage.py

Read the contributing guide first, especially the safety rules.

Try the wizard without hardware Now

The guided wizard is what volunteers will use. You can explore it today on the built-in console emulator and a simulated hall. Nothing leaves your computer: no console is touched and no sound is played.

Start it

From a clone with uv installed, on the m3-wizard branch (see Install and step 3):

uv sync
CTUNE_DEV_SAFE=1 uv run ctune --emulator --audio fake --home /tmp/ctune-demo                                  # full-screen wizard
CTUNE_DEV_SAFE=1 uv run ctune --emulator --audio fake --home /tmp/ctune-demo wizard --plain --lang uk         # line interface, in Ukrainian
CTUNE_DEV_SAFE=1 uv run ctune --emulator --audio fake --home /tmp/ctune-demo resume                           # continue the saved session

--emulator uses the built-in console emulator, --audio fake the simulated hall, and --home keeps the demo files apart from real ones (without it they go to ~/ChurchTune). --lang takes en, ru or uk. The line interface (--plain) works with screen readers and in scripts.

Keys

  • Ctrl+C or Space: stop the sound at once, on every screen.
  • Esc: go back one step, where the screen allows it.
  • Ctrl+Q: save and quit. Continue later with ctune resume.
  • In the line interface: Enter takes the recommended answer, B goes back, Q saves and quits, and Ctrl+C stops the sound, saves and quits.

What the wizard does today

13 steps, or 12 with one microphone. The progress is saved after every step.

  1. Start: the name of the hall and what you want to do today.
  2. Mac check: the computer and the console's USB audio card.
  3. Console: finds the console on the network, asks you to confirm it and checks the connection.
  4. Reading the console: reads all its settings without changing anything, then asks you to save a scene on the console.
  5. Speakers: shows which output feeds the main speakers, the subwoofer, the monitors and so on, and asks you to confirm the outputs it is not sure about.
  6. Equipment: a few questions the console cannot answer: active or passive speakers, size of the listening area, how many measurement microphones and which model.
  7. Microphones: you scratch each microphone and it finds which input it is on. It tells you what to do on the console, for example switch on +48V or mute that channel.
  8. Playback path: checks that the computer's sound goes to the hall speakers, not to the monitors or the stream.
  9. Level: sets a safe measuring level.
  10. Microphone calibration: only with several microphones; compares them against each other.
  11. Measurement rounds: test sweeps at the spots in the room.
  12. Results: what was measured, in plain words.
  13. What next: what to do after this session.

Safety before any sound

  • The wizard never mutes or unmutes anything itself. On a real console you mute the measurement microphone channels by hand, and it tells you which ones.
  • Before the first sound it reads the console again. While a channel that listens to a measurement microphone is unmuted and can reach the speakers, it refuses to make any sound, because that could cause feedback.
  • This check sees channels. A microphone routed straight to an output, bypassing a channel, is not checked yet, so check your routing yourself.
  • Every sound has a warning screen first (“Play the test sound” or “Not yet”), and measurement rounds count down 3 seconds.

What you will see in the demo

In the emulator the measurement microphone's channel (channel 12) starts unmuted, and the emulator cannot be muted by hand yet. So the demo stops at the Playback path step with the message “Channel 12 still sends a measurement microphone to the speakers. Mute it on the console, then press Enter.” Pressing Enter again only repeats the check. This is the safety rule at work, not a fault. Explore the first steps, then save and quit (Ctrl+Q, or Q in the line interface).

What it does not do yet

  • It does not propose any changes: crossover, subwoofer level and timing, system EQ (milestone M4).
  • It does not write anything to the console, and there is no apply, undo or verify yet (M5).
  • The speaker-by-speaker check and the separate subwoofer and main-speaker measurement need temporary mutes, so they come into the wizard with M5. They exist today only as expert commands.
  • No report file yet (M6).
  • It has not been run at a real console yet. That is part of the pilot (M7).

For console owners: hardware checks

Some console behaviour can only be confirmed by a person at a real console. Each check is one row of the hardware checklist. Your report moves a feature from “advice only” to “ChurchTune may write this” for that model and firmware.

Before you start

  • Use an empty hall, never during a service or rehearsal.
  • Keep the system at a safe, low level.
  • Save a scene on the console first, so you can restore everything.
  • Install the developer version on the Mac (see Install above) and connect it to the console's network.

Steps

  1. Open the hardware checklist and pick a row for your console. Rows 1 and 2 (ctune hwcheck delay and ctune hwcheck polarity) can be run today; others depend on features that are still being built.
  2. Read the row: what to verify, the command, and the expected result.
  3. Run the command and watch the console screen. Compare what happens with the expected result.
  4. Restore the old value as the row describes (with the undo file, or by recalling your scene).
  5. Report the result with the hardware check form: the row number, your console model and firmware, the ChurchTune commit (git rev-parse --short HEAD) and what you saw.

Console dumps

Read-only dumps of other models, firmware versions and routings help the console driver (M1) recognise more systems. Remove names and anything personal first; the contributing guide explains how.

Coming later: tuning your system Coming later

This is how the complete wizard is planned to work once milestones M4–M6 are done. The first two steps, reading the console and measuring, are already in the wizard (see above); the rest is still being built.

  1. Read the console. ChurchTune finds the console and shows what it found, for example “X32 Producer, main speakers on Matrix 1/2, subwoofer on Matrix 3. Correct?”. It asks only what it cannot read.
  2. Measure. It finds the microphone input, checks the signal path with a short quiet tone, sets the level, then shows a simple map of spots and guides you: “put the microphone here, press Enter”.
  3. Analyse. It averages the spots and checks the room, including how long it rings and where the subwoofer meets the main speakers.
  4. Propose. It shows the problems in plain words and suggests a few changes, each with a short “why”.
  5. Apply. You see every change, confirm by typing, an undo file is saved first, and each value is read back.
  6. Verify and report. It measures again, shows before and after, offers to undo if it is not better, saves a report and reminds you to save a scene on the console.
