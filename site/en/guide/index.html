Guide

Using ChurchTune today

An honest guide to what you can do now, and what is coming. It grows with every milestone.

Last updated: 15 October 2026

Pre-alpha. The guided wizard reads the console, measures, proposes changes and can write them, with undo and a check measurement, and at the end it writes a report. Writing to a real console has not been verified on hardware yet: all of it is tested only against the emulator and a simulated hall. It runs from the source code only. Do not use it on your church's live system yet. See the roadmap.

What you can do today Now

  • Anyone comfortable with a terminal can try the guided wizard on the built-in console emulator with a simulated hall: no console, no speakers, no sound. See Try the wizard without hardware.
  • Developers and testers can install the project, run the tests and try the expert command line against the emulator.
  • Console owners can run a hardware check at a real X32 or M32 and report the result. This is the most valuable help right now.
  • Developers can follow the wizard all the way on the emulator: the subwoofer and main-speaker measurement, applying the changes, the check measurement and the report at the end (see What you will see in the demo and The report). They can also apply a change plan and undo it from the terminal (see Apply and undo from the terminal).
  • Volunteers who want to tune their church system: please wait. The wizard can now write the changes, but this has been tested only against the emulator, never on a real console (milestone M5 is done, but the hardware checks are still open). Watch releases on GitHub to hear when it is ready.

Equipment you will need

For the real tuning, later. Nothing here is needed to try the developer version.

  • A Mac (the app is made for macOS).
  • A Behringer X32 or Midas M32 with firmware 4.x and a USB audio card: X-USB or X-LIVE in an X32, DN32-USB or DN32-LIVE in an M32. The test sounds are played and recorded through this card.
  • A USB cable from the Mac to the console, and a network connection (cable or Wi-Fi) to the console, which ChurchTune uses to read its settings.
  • A measurement microphone, for example a Behringer ECM8000, with a stand and an XLR cable to a console input. ChurchTune can also use several microphones at once and calibrate them against each other; this has been tested only with simulated microphones so far.
  • An empty, quiet hall and about 1–2 hours.

For developers and testers

Everything below runs only against an emulator on your own computer and simulated audio. Always put CTUNE_DEV_SAFE=1 in front of commands that run the app or the tests: the code then refuses any real console and any real audio device.

1. Install

You need macOS or Linux, Python 3.12 and uv (uv can install Python for you). On Debian or Ubuntu also install libportaudio2 libsndfile1.

git clone https://github.com/mihailShumilov/ChurchAutoTune.git
cd ChurchAutoTune
uv sync

2. Run the tests

CTUNE_DEV_SAFE=1 uv run pytest -q                # all tests: console emulator + simulated audio
CTUNE_DEV_SAFE=1 uv run pytest tests/golden -q   # the real hall session of 2026-10-02

3. Try the expert command line on the emulator

Everything up to M5 is on the main branch. The report (M6) is still in review: until it is merged, ctune report and the report at the end of the wizard live only on the m6-report branch. To try them, in your clone:

git checkout m6-report
uv sync

The quickest way is the global --emulator option: it starts a console emulator inside the program for that one command.

CTUNE_DEV_SAFE=1 uv run ctune --emulator doctor     # check the computer and the console, explain the speaker layout
CTUNE_DEV_SAFE=1 uv run ctune --help                # all commands

You can also run the emulator on its own in one terminal (it prints its port and runs until Ctrl+C) and point commands at it from a second terminal, replacing PORT:

CTUNE_DEV_SAFE=1 uv run ctune emulator --model X32P
CTUNE_DEV_SAFE=1 uv run ctune --console 127.0.0.1:PORT --audio fake --home /tmp/ctune-demo doctor

The output of most expert commands is still in Russian; the wizard below is translated. The expert command line stays as a tool for developers next to the wizard.

4. Before a pull request

CTUNE_DEV_SAFE=1 uv run ruff format --check . && uv run ruff check . && uv run mypy \
  && CTUNE_DEV_SAFE=1 uv run pytest --cov --cov-report=json && uv run python scripts/check_coverage.py

Read the contributing guide first, especially the safety rules.

Try the wizard without hardware Now

The guided wizard is what volunteers will use. You can explore it today on the built-in console emulator and a simulated hall. Nothing leaves your computer: no console is touched and no sound is played.

Writing to a real console is not verified on hardware yet. The steps that write to the console have been tested only against the emulator and a simulated hall. Do not run them on your church's console until people have done the hardware checks in a real hall (rows 22–28 of the hardware checklist).

Start it

From a clone with uv installed, on the main branch (or m6-report for the report; see Install and step 3):

uv sync
CTUNE_DEV_SAFE=1 uv run ctune --emulator --audio fake --home /tmp/ctune-demo                                  # full-screen wizard
CTUNE_DEV_SAFE=1 uv run ctune --emulator --audio fake --home /tmp/ctune-demo wizard --plain --lang uk         # line interface, in Ukrainian
CTUNE_DEV_SAFE=1 uv run ctune --emulator --audio fake --home /tmp/ctune-demo resume                           # continue the saved session

--emulator uses the built-in console emulator, --audio fake the simulated hall, and --home keeps the demo files apart from real ones (without it they go to ~/ChurchTune). --lang takes en, ru or uk. The line interface (--plain) works with screen readers and in scripts.

Keys

  • Ctrl+C or Space: stop the sound at once, on every screen.
  • Esc: go back one step, where the screen allows it.
  • Ctrl+Q: save and quit. Continue later with ctune resume.
  • In the line interface: Enter takes the recommended answer, B goes back, Q saves and quits, and Ctrl+C stops the sound, saves and quits.

What the wizard does today

16 steps, or 15 with one microphone. The steps “Subwoofer and main speakers apart”, “Apply the changes” and “Check measurement” come only when you choose to change the system (full setup, or only the subwoofer); the first of them only when the system has a subwoofer. The progress is saved after every step.

  1. Start: the name of the hall and what you want to do today.
  2. Mac check: the computer and the console's USB audio card.
  3. Console: finds the console on the network, asks you to confirm it and checks the connection.
  4. Reading the console: reads all its settings without changing anything, then asks you to save a scene on the console.
  5. Speakers: shows which output feeds the main speakers, the subwoofer, the monitors and so on, and asks you to confirm the outputs it is not sure about.
  6. Equipment: a few questions the console cannot answer: active or passive speakers, size of the listening area (width × depth in metres, for the point plan; leave it empty for a standard plan), how many measurement microphones and which model.
  7. Microphones: you scratch each microphone and it finds which input it is on. It tells you what to do on the console, for example switch on +48V or mute that channel.
  8. Playback path: checks that the computer's sound goes to the hall speakers, not to the monitors or the stream.
  9. Level: sets a safe measuring level.
  10. Microphone calibration: only with several microphones; compares them against each other.
  11. Measurement: a plan of places in the hall, then test sweeps at each place (see below).
  12. Subwoofer and main speakers apart: at a few places it measures the subwoofer alone, the main speakers alone and everything together, with short mutes after a typed word (see below).
  13. Results and proposals: what was measured, in plain words, then the change packages and advice on the input channels (see below).
  14. Apply the changes: writes the packages you chose, after a fresh read of the console and a typed word (see below).
  15. Check measurement: measures some seats again and says whether it got better (see below).
  16. What next: what to do after this session, including saving the scene on the console under a new name. Then it writes the report (see below).

The measurement point plan

Before the measurement rounds the wizard makes a plan of places where people sit:

  • At least 8 seats in the middle part of the hall, off the centre aisle, at uneven distances from each other.
  • Each place is described in words with distances, for example “front rows, left, about 6 m from the stage, 3.5 m left of the centre aisle”. Left and right are as you face the stage.
  • A simple map of the hall shows the stage at the top and numbers only the places of the current round.
  • The microphone goes at the ear height of a seated person (1.2 m), pointing at the stage. After Enter you have 3 seconds to step at least 2 m away.
  • If you gave no hall size, the plan is for a typical 12 × 18 m hall and you place the microphones roughly.
  • The plan is kept for the venue, so a later check measurement can use the same places.

The subwoofer and the main speakers apart

To find out where the subwoofer meets the main speakers, and whether they cancel each other there, the wizard measures them apart at the junction places of the plan. At each place it plays three sweeps in a row: the subwoofer alone, the main speakers alone, then everything together.

  • For this the program mutes the subwoofer or the main speakers on the console for a few seconds. It mutes only their matrices (the outputs that feed the speakers), never Main LR and never an input channel.
  • It asks first. To allow the short mutes you type the word mute (in the Russian interface заглушить, in the Ukrainian one заглушити) and press Enter. An empty line skips this measurement; then no crossover is proposed.
  • Before the first mute it reads the console and saves how every switch was. Right after the three sweeps it puts every switch back, also when you stop the sound with Ctrl+C or Space.
  • If a run was interrupted before the switches came back (for example the computer lost the connection), the wizard puts them back first the next time: it reads the console again, shows what it would switch back on and asks for the same word. If the console does not confirm, it tells you which matrices to switch on by hand.
  • This works only when the subwoofer and the main speakers each come from their own matrix. Otherwise the wizard says so, skips this measurement and does not propose a crossover.

Change packages and channel advice

After the results the wizard proposes changes in packages. Each package has its own screen:

  • a table of what changes: where, the value now and the proposed value;
  • why the change helps, the expected effect and the risk;
  • the question “Add … to the change plan?”, with “Add to plan” or “Leave it out”.

When you leave a package out, the packages after it are designed again without it, so nothing in the plan depends on a change you did not choose. Your choices are saved in the session folder as proposal.json.

With the subwoofer and the main speakers measured apart, the wizard can propose up to four packages, in this order:

  • the crossover: the low notes go only to the subwoofer and the rest only to the main speakers;
  • the subwoofer alignment: a small delay and maybe a polarity flip, so they arrive together. This one is advice only: you set it by hand on the console;
  • the subwoofer level, so both are about equally loud where they meet;
  • the system EQ: gentle corrections for what the hall does to the sound in most seats. Narrow dips at single seats are left alone, because EQ cannot fix them.

Without that measurement (you skipped it, or the speakers do not come from their own matrices) the wizard proposes only the system EQ and says why: set blind, a crossover can leave a gap in the bass. Around the crossover the console already has, that EQ then only turns the sound down a little over a wide range, and it never makes any one seat clearly worse.

Then comes advice on the input channels. The program never changes these itself; you decide by ear, one setting at a time, at a rehearsal:

  • voices without a low cut (high-pass filter), or with a very high one;
  • narrow cuts that probably protect against feedback: make them at most half as deep, at a rehearsal, with the monitors on;
  • cuts shared by many channels;
  • very deep cuts: check whether they are still needed, 3 dB at a time;
  • big boosts, which can cause feedback;
  • phantom power (+48V) on what looks like a dynamic microphone: switch it off only while the channel is muted.

Nothing is written to the console at this step. Writing comes in the next step, “Apply the changes”.

Applying the changes

After the proposals, the step Apply the changes writes the packages you chose:

  • First it reads the console again. If someone changed a setting since the measurement, it refuses the plan and asks you to measure again, so the plan always fits what the console has now.
  • It shows every setting it will write, with the value now and the new value, in the order it will write them.
  • To write, you type the word apply (in the Russian interface применить, in the Ukrainian one застосувати) and press Enter. Anything else cancels, and nothing is written.
  • The old values are saved in an undo file before the first write.
  • The order of the writes is chosen so the sound never gets louder in between. When a crossover cannot be reached that way, the program mutes the subwoofer's or the main speakers' matrix for a moment while it changes it: you hear a short dropout of the subwoofer or the main speakers, never a jump up.
  • If the new subwoofer level is more than 12 dB away from where it was when the program first read this hall, it asks a separate question first (the safe answer is “no”).
  • Every value is read back from the console. If one does not read back, the wizard stops there and offers to put back what was written.
  • Output delay and polarity are not written by the program. Right after the writes it shows them as values for you to set by hand on the console, before the check measurement.

The check measurement

Then the step Check measurement measures at least four seats again, among them the seat that sounded worst and the one in the middle of the hall. Put the microphones exactly where they stood before. By fixed rules it says one of three things: better, no noticeable difference or worse, with a small before and after picture. When it got worse, it recommends putting the old values back and offers to do it right away.

The last screen reminds you to save the scene on the console under a new name (for example with today's date), so the new settings survive a restart. It also shows the command that puts the old values back later.

The report

At the end the wizard writes a report of the session, in the language of the interface (English, Russian or Ukrainian). It goes into the session folder, in a folder called report:

  • report.html: the report in one file. It opens in any browser without internet, follows the light or dark theme of your computer and prints well.
  • report.md with its charts: the same report as plain text.
  • report.json: the same data for other programs.
  • for-chat.txt: a short text to paste into a chat or forum when you ask someone for advice.

The report has these parts: a summary, the system, how good the measurement was at each place, the frequency response before and after, where the subwoofer meets the main speakers, reverberation for speech and for music, what was changed (with the command that undoes it), the check measurement, advice on the input channels, what the room itself could use, a checklist for the next service, and technical details.

The wizard prints where the report is and an open "…" command: paste it into the terminal and the report opens in your browser. You can make the report again at any time from the saved session, without a console. Without a session folder it takes the newest session:

CTUNE_DEV_SAFE=1 uv run ctune --home /tmp/ctune-demo report               # write the report of the newest session again
CTUNE_DEV_SAFE=1 uv run ctune --home /tmp/ctune-demo report --lang uk     # write it again in Ukrainian
CTUNE_DEV_SAFE=1 uv run ctune --home /tmp/ctune-demo report --for-chat    # print the short text for a chat
CTUNE_DEV_SAFE=1 uv run ctune --home /tmp/ctune-demo report SESSION       # the report of one particular session

The report is still in review (M6). Until it is merged, it is only on the m6-report branch (see step 3).

Apply and undo from the terminal

The expert command line does the same: ctune apply-packages writes the chosen packages of a saved proposal.json, and ctune undo puts the old values back. Use them only with the emulator and CTUNE_DEV_SAFE=1. They need a proposal.json from a wizard session (in the session folder, <home>/venues/<hall>/sessions/<time>-<goal>/). The easiest way to get one is to run the emulator demo up to the proposals (see below).

First look without writing anything. --dry-run shows the settings it would write, in order, and stops:

CTUNE_DEV_SAFE=1 uv run ctune --emulator apply-packages SESSION/proposal.json --dry-run

--emulator starts a fresh emulator for that one command only. To write and then undo, keep one emulator running in its own terminal (it prints its port) and point both commands at it, replacing PORT, SESSION and UNDO_FILE:

CTUNE_DEV_SAFE=1 uv run ctune emulator --model X32P
CTUNE_DEV_SAFE=1 uv run ctune --console 127.0.0.1:PORT --audio fake --home /tmp/ctune-demo apply-packages SESSION/proposal.json
CTUNE_DEV_SAFE=1 uv run ctune --console 127.0.0.1:PORT --audio fake --home /tmp/ctune-demo undo UNDO_FILE

apply-packages saves the undo file before the first write and prints its name (it is in the undo folder under --home). undo puts back only the values that were not changed by hand since, and lists the ones it leaves alone. Both commands also take --dry-run. Their texts are still in Russian, so they ask for the Russian words применить (apply) and вернуть (put back). For scripts, apply-packages --yes-i-am-at-the-console confirms without the typed word; everything else stays the same (the fresh read, the undo file, the readback).

Safety before any sound

  • The wizard never mutes or unmutes an input channel. On a real console you mute the measurement microphone channels by hand, and it tells you which ones. The only things it mutes itself are the speaker matrices, for a few seconds, after a typed word (see above), and during a write when there is no other safe order.
  • Before the first sound it reads the console again. While a channel that listens to a measurement microphone is unmuted and can reach the speakers, it refuses to make any sound, because that could cause feedback.
  • This check sees channels. A microphone routed straight to an output, bypassing a channel, is not checked yet, so check your routing yourself.
  • Every sound has a warning screen first (“Play the test sound” or “Not yet”), and measurement rounds count down 3 seconds.

What you will see in the demo

The demo goes through the whole wizard. Nobody can press the emulator's buttons, so at the start the demo mutes the channels of its measurement microphones itself, as a person would on a real console. The simulated hall listens to the emulator: the test sound goes through the Main LR EQ, and each speaker plays only while its matrix is switched on.

So you can follow every step: the point plan, the subwoofer and main-speaker measurement with its short mutes, the change packages (with the crossover), applying, the check measurement and the last screen with the report. Choose the full setup (or only the subwoofer) at the start to reach the steps that write. Save and quit at any time with Ctrl+Q (Q in the line interface). On a real console the wizard does not mute the microphone channels for you: there it waits until you do it.

What it does not do yet

  • It never writes output delay or polarity: they stay values for you to set by hand until they are checked on a real console.
  • The speaker-by-speaker check is not in the wizard yet. Today it exists only as an expert command.
  • The report is still in review (M6), so for now it is only on the m6-report branch (see The report).
  • It has not been run at a real console yet, and writing to a real console is not verified on hardware. That needs the hardware checks and the pilot (M7).

For console owners: hardware checks

Some console behaviour can only be confirmed by a person at a real console. Each check is one row of the hardware checklist. Your report moves a feature from “advice only” to “ChurchTune may write this” for that model and firmware.

Before you start

  • Use an empty hall, never during a service or rehearsal.
  • Keep the system at a safe, low level.
  • Save a scene on the console first, so you can restore everything.
  • Install the developer version on the Mac (see Install above) and connect it to the console's network.

Steps

  1. Open the hardware checklist and pick a row for your console. Rows 1 and 2 (ctune hwcheck delay and ctune hwcheck polarity) can be run today; others depend on features that are still being built. Rows 22–28 check the new writing of M5 (applying, undo, the check measurement, the short matrix mutes, the subwoofer and main-speaker measurement and the crossover); they are on the main branch, and a person must run them in an empty hall before anyone relies on these writes.
  2. Read the row: what to verify, the command, and the expected result.
  3. Run the command and watch the console screen. Compare what happens with the expected result.
  4. Restore the old value as the row describes (with the undo file, or by recalling your scene).
  5. Report the result with the hardware check form: the row number, your console model and firmware, the ChurchTune commit (git rev-parse --short HEAD) and what you saw.

Console dumps

Read-only dumps of other models, firmware versions and routings help the console driver (M1) recognise more systems. Remove names and anything personal first; the contributing guide explains how.

Coming later: tuning your system Coming later

This is how the complete wizard is planned to work in a real hall once the hardware checks and the pilot (M7) are done. All six steps are already in the wizard (see above; the report is still in review), but they have been tried only on the emulator and a simulated hall.

Writing to a real console is not verified on hardware yet. Applying, undo, the short mutes and the check measurement have been tested only against the emulator and a simulated hall. Wait until the hardware checks are done before you use them on your church's system.

  1. Read the console. ChurchTune finds the console and shows what it found, for example “X32 Producer, main speakers on Matrix 1/2, subwoofer on Matrix 3. Correct?”. It asks only what it cannot read.
  2. Measure. It finds the microphone input, checks the signal path with a short quiet tone, sets the level, then shows a simple map of spots and guides you: “put the microphone here, press Enter”.
  3. Analyse. It averages the spots and checks the room, including how long it rings and where the subwoofer meets the main speakers.
  4. Propose. It shows the problems in plain words and suggests a few changes, each with a short “why”.
  5. Apply. You see every change, confirm by typing, an undo file is saved first, and each value is read back.
  6. Verify and report. It measures again, shows before and after, offers to undo if it is not better, saves a report and reminds you to save a scene on the console.
